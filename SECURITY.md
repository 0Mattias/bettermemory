# Security policy

## Supported versions

bettermemory follows semver from 1.0 onward. The latest minor of the current major gets security fixes; older majors and earlier minors do not. Concretely:

| Version | Status |
|---------|--------|
| 9.x latest | Supported |
| 9.x earlier minor | Upgrade to latest 9.x |
| 8.x | Unsupported; upgrade to 9.x and run `bettermemory migrate v8` once per store directory (the 8.x files are read, never written) |
| 7.x and earlier | Unsupported; upgrade to 9.x. No on-disk change between 1.x and 8.x (`models.SCHEMA_VERSION` stayed at 1), so the 8.x migration reads these directories too |
| 0.x | Unsupported (pre-1.0) |

Upgrading across 4.0, 5.0 or 6.0 costs no data migration but does lose surface: 4.0 removed the embedding lane (the `"semantic"` search mode, both embedding extras, `[behavior] semantic_provider` and `semantic_dedup`), 5.0 removed the web UI (`bettermemory ui`, the `[ui]` extra), and 6.0 removed the embedding lane again after its 5.5.0 opt-in reentry (the `[embeddings]` and `[embeddings-fast]` extras). 7.0 removed nothing and changed one default: `episode_handoff` rows carry `body` only when `include_bodies=True` is passed. 8.0 made a `user-inference` write commit on the first call. 9.0 replaced the markdown directory with one SQLite file, reduced twenty-seven tools (eighteen registered by default) to nine and removed the sync lane; a server pointed at an un-migrated 8.x directory refuses to start and names the migration. See the release notes for each.

## Reporting a vulnerability

**Please do not file a public GitHub issue.** Report it privately through [GitHub private vulnerability reporting](https://github.com/0Mattias/bettermemory/security/advisories/new) on this repository, or by email to hello@anaphase.ai.

Include in the report:

- A description of the issue and its impact (what does an attacker gain?).
- A reproduction: minimal repo, command, or input that triggers the behavior.
- The bettermemory version (`bettermemory --version`) and the OS or Python version where you observed it.
- Optional: a proposed fix.

You will get an acknowledgement within seven days. The expected timeline for a fix depends on severity:

- **Critical** (RCE, arbitrary file write outside the storage dir, exfiltration of memory contents, access to the daemon's API without its token): hotfix release within two weeks of confirmation, with an advisory.
- **High** (denial of service against a user's local store, integrity break on a stored record): fix in the next minor release, with an advisory if there is no acceptable workaround.
- **Medium or low**: addressed in the normal release cadence.

## Threat model

bettermemory is a single-user, local-first tool. The store is one SQLite file, `memory.sqlite`, whose tables are the fold of a hash-chained log: every record row was produced by a signed log row and points at it. "Signed" means an HMAC-SHA256 under a per-store key, 32 random bytes kept under the user's config directory (`keys/<store_id>.key`) and never in the store; the key is symmetric, so a process that can read it can sign. Everything the store believes about a memory is in that file: its body, its scopes, and the trust fields (`last_verified_at`, `source`, `confidence`, `claims`, the `verified_*` attestations). The threat model is therefore organised around two questions: who can write into the store file, and who holds the key.

### The attackers

**The user.** Trying not to lock themselves out: data integrity, no corruption, no data loss under normal operation and concurrent access. Every mutation is one SQLite transaction that appends the log row and applies it to its table together, and tombstones make removals restorable.

**A process running as the same user with write access to the store file but not the key.** OS filesystem permissions are the access control: the store directory is created `0o700`, the store file `0o600`. bettermemory does not encrypt at rest, and the daemon's bearer token is its only caller check. What the store believes about a row such a writer inserts:

- **Provenance at read.** Every memories, tombstones and episodes row carries the MAC of the log row that produced it, and every search, show and handoff verifies that pointer: the log row exists, it is of the producing kind, its payload names the record, and its MAC verifies under the key of the log segment it sits in. A row inserted around the tool has no such row and reads `unaccounted`; a log row appended without the key fails its MAC and the row pointing at it reads `unaccounted` the same way. The label rides every read surface and the recall hook's pointer, and the health report lists the unaccounted records.
- **Segments and the origin anchor** (9.0.0rc12). The log splits into segments at its `rekey` rows, and a segment is *held* when this machine's key ring, current or retired keys, has its key. A segment that is not held and comes after a held one is *foreign*: rows put into history this machine signed by someone without its key, who can write a `rekey` row naming any key and make the rows after it verify under a key of their own. A foreign segment's records read `unaccounted`, whether or not the writer also edited `meta.key_fingerprint` to match, and on the commands that only read the store (`memory history`, `export`, `stats`, `session-start`) as on the server's; a row this machine's own current key signed into it (a daemon that had the store open while the forged row went in) still reads `local`. The segments before the first held one are a store copied here without its key and keep their labels (see the remote writer, below). Where this machine's history begins is not taken from the log alone, since the same writer can rewrite that row too: the key ring keeps `<store_id>.origin` beside the key, the seq and MAC of the first row this machine's key ring signed. When the row at that seq is gone, carries another MAC or verifies under no held key, every segment that is not held reads `unaccounted`, leading ones included. A record whose log row sits below seq 1 reads `unaccounted` too.
- **When a planted row is detected.** On the next search, and not silently trusted, in each of these cases, which `tests/test_segment_trust.py` and `tests/test_origin_anchor.py` pin: a row inserted around the store; a log row forged without the key; a forged segment after this machine's rows, with or without the `meta` edit; and, on a store that holds an origin anchor, that segment with the row where this machine's history begins rewritten as well, on a store created here or one copied in. The integrity benchmark inserts memories around the write API with a forged log row: 10 of 10 forged memories are caught, against 0 of 10 in 8.0 (the frozen result artifacts under `bench/integrity/results/`). By default it is **not** detected in three cases. (1) The anchor is written at a store's first writing open under 9.0.0rc12 (trust on first use): an edit made before that open is taken as it stands, so the rewritten-start variant made then passes, while the plain forged segment is still caught. (2) An editor who replaces `meta.store_id` with a fresh id detaches the store from this machine's key ring: the next open takes it for a store copied here, anchors its own `rekey` row, and every earlier row, planted ones included, leads and keeps its label; `log verify` reads `unverifiable`. (3) The rows of a store that really was copied here keep the labels they arrived with. `[security] strict_provenance = true` reads all three `unaccounted`: only what this machine's own keys verify is trusted.
- **The chain audit.** `bettermemory log verify` walks every row from seq 1, checks every MAC and every link to the row before, compares the head checkpoint and the origin anchor kept beside the key, and refolds the log to compare every table against it. An edited row, a deleted row, a deleted tail, a table row no log row accounts for, a foreign segment (`foreign_segment`) and a rewritten start of this machine's history (`origin_mismatch`) are each reported as tampering, exit status 1; a leading segment signed by a key this machine does not hold reads `unverifiable`. The command never writes.
- **The store id.** The key ring names its files after the store id in `meta`, so a store whose id is not the 32 lowercase hex characters `create` writes is refused at open: a path-shaped id would otherwise bind a key the writer planted beside the store as the store's own.
- **Detect-only.** None of this stops a write. A writer with the file can still edit a body in place; the edit is reported by the audit and, when the edit touches a row's pointer, at the next read. Treat the store file's integrity as equal to the host account's integrity.
- **Write-time supersession is a lever.** A claim-sized statement admitted through the write API that carries a change cue and a value against a stored claim earns a `supersedes` link over it, so a false statement can mark the true one superseded, and the integrity benchmark measures how often. The link note names the cue and both values, every detector-set link is in the log under `supersedes_detected`, and `memory_update(links=[])` on the new record clears it. The lever is bounded by admission, and `[behavior] write_supersession = false` removes it.

**A process that holds the key.** The key file is owner-only, and every process running as the user is its owner; the store cannot tell the rows such a process signs from the tool's own. There is no defence against the user's own account; tamper evidence is against a writer who reaches the file but not the config directory (a synced or copied store file, a backup restored elsewhere, a process confined to the store directory), and against accidents. The same goes for the files beside the key: a process that can write the keys directory can move or delete the head checkpoint and the origin anchor, and with them what `log verify` compares against.

What a team can keep is evidence after the fact. `bettermemory log anchor` takes an anchor of the log (the store id, the last row's seq and MAC, and a SHA-256 over every row's MAC up to it), and `bettermemory log verify --anchor FILE` reports `anchor_mismatch` when the log no longer holds that seq with the same MAC and digest: history at or below an anchored seq was rewritten or deleted, by a key holder too, and a deleted tail is caught even when the head checkpoint was rewound to match. Its limits: rows after the newest anchor are pinned by nothing but the key; an attacker who can also rewrite the stored anchors defeats them, so keep them off the host (a ticket, a private repository, a WORM bucket, the SIEM); an anchor discloses the store id, a seq and MACs, never content or the key. The store id is not a secret, and knowing it is not harmless: see a repository that carries a store, below.

**A local process that reaches the daemon.** One daemon per store listens on 127.0.0.1 only (`[daemon] port`, default 7397) and serves the nine tools at `/mcp`, the hook bodies at `/api/v1/hook/<event>`, `/health` and `/api/v1/admin/shutdown`. Every request except `GET /health` must carry the bearer token from the daemon's state file (`daemon-<store hash>.json` under the user's state directory or `BETTERMEMORY_STATE_DIR`; directory `0o700`, file `0o600`, the daemon's log `0o600`). The token lives behind the same account boundary as the store file and the key. The stdio `bettermemory` process an MCP client spawns forwards to the daemon with that token, and serves the store in-process when no daemon can be reached or started.

- **Host and Origin on every route** (9.0.0rc12). Every route, `/health` and the hook and admin routes as well as `/mcp`, answers 421 unless the Host header is `127.0.0.1`, `localhost` or `[::1]`, bare or with the daemon's own port, and 403 for an Origin header, when one is sent, that is not `http://` with one of those hosts; an empty Origin is refused. A page a browser loads through a rebound DNS name can therefore neither read `/health` nor post to the hooks. The MCP SDK's own check stays on under `/mcp`. A client that reaches the daemon through a local port-forward or on another localhost port is refused too. Bodies under `/api/v1/` are capped at 4 MiB, the SDK's `/mcp` cap (413), and websocket upgrades are closed.
- **What `/health` discloses.** Without the token it answers the daemon's version, pid, store path and the paths of any saved orphan stores. Any local account can read these, so they are not secrets, and nothing below treats them as one.
- **The daemon proves its token** (9.0.0rc12). Before a client sends anything that carries the token or a payload, it asks `/health?nonce=<fresh hex>`, and the daemon answers `proof`, an HMAC-SHA256 of the nonce under the token, which reveals nothing about the token. The hook client, the shim, `up`, `down`, `status` and the service install check it. A daemon writes `"health_proof": 1` into its state file, and at the port of such a file a reply without a valid proof is another process, for example a listener that took the port after the daemon crashed, under this account or another: it gets no hook payload, no token, no shutdown request and no signal, and the client starts a daemon beside it. A state file written by a daemon before 9.0.0rc12 has no such key, and a reply without a proof that repeats that file's pid and store is accepted as that older daemon; since `/health` discloses both, a listener that read them before the crash can pass for it until a newer daemon rewrites the file. A long-running shim posts to the port it already knows without a new proof, so a listener that takes a crashed daemon's port before the shim's next call receives that one call, token included; a 401 or a connection error on a later call makes the shim look the daemon up again, and the proof then holds.
- **Signals and proxies.** A stop signals the state file's pid only when the daemon at the port proved itself, or when that pid is alive while the store's lock is held: never on a state file alone, whose pid the OS may have given to another process. The client's requests to the daemon go through no HTTP proxy, whatever `http_proxy` or `ALL_PROXY` say.

**A client that lies about who it is.** Every write records who made it (`actor`) and which channel named the workspace (`origin.source`); see `docs/api.md` under Identity. Every declared field (an `x-bettermemory-*` header, a `BETTERMEMORY_*` variable in the server's environment, the `initialize` handshake's `clientInfo`) is client input and is stored as such, with its channel beside it. Only `actor.principal` is attested: it is read solely through the SDK's `authenticated_principal`, the identity of a verified OAuth token on an HTTP transport, and it is `null` everywhere else. A declared value cannot reach that field by any path, and `tests/test_identity.py` pins it. Since 9.0.0rc12 declared values are stripped of Unicode format characters (bidi controls, zero-width characters) before they are stored, so a declared name cannot be made to render as another; the workspace path and the attested principal are kept code point for code point. The CLI's own declarations (`project join`, `new`, `init`, `memory move`) name the OS user from the password database by the real uid on POSIX, `os:<name>` (or `os:uid:<n>` without an entry), not from `$USER`; on Windows the name still comes from `getpass`, which reads a variable the caller sets. What the label buys is what provenance buys: a memory that says it came from one client is a claim the reader can weigh, not a fact the store vouches for. Identity is evidence, never a permission: `memory_show(id)` stays unrestricted, and the per-client session isolation it keys (disabled scopes, use tokens) separates clients that declare differently; it is not a boundary against a client that declares another client's name.

**A remote writer.** 9.0 ships no cross-host lane: no sync, no pull, no admission. A store file copied from another machine arrives without its key. The server writes a new key for it, appends a `rekey` row, anchors this host's history at that row and logs a warning; rows signed under the old key keep their stored labels, because their pointers cannot be checked here, and `log verify` reports the store `unverifiable`. With `[security] strict_provenance = true` they read `unaccounted` instead. Two cases read as tampering on purpose. A store moved away and back, or opened once under another `BETTERMEMORY_KEYS_DIR` (which rekeys it), holds the other key's segment after this host's own, the foreign shape; filing that key in this host's keys directory as a retired key, `<store_id>.<first 16 hex characters of its fingerprint>.key`, restores `ok`. A store file copied from its source machine over this host's copy again changes the history at the origin anchor and reads `origin_mismatch`; `bettermemory backup restore` of a bundle, or deleting `<store_id>.origin` and `<store_id>.head` from the keys directory, accepts the replaced history, which trusts the file again on purpose. An 8.x directory is read only by `bettermemory migrate v8`, which imports its records as `imported` rows under this host's key: the migration is the one path a foreign record takes into the store, and its rows are this host's own record of that directory, not a claim about who wrote the files.

**A repository that carries a store.** The store-directory rule's third step makes `./.claude-memory/` in the working directory the store when it exists, so a cloned repository that commits that directory becomes the user's store inside that checkout: its memories reach the session brief and the prompt recall, and the user's own writes there land in its working tree. Its rows were signed under a key this host does not hold, so they read like a copied store's: labels kept unless `strict_provenance` is on. `[storage] cwd_store = false` (9.0.0rc12) skips that step, leaving `BETTERMEMORY_DIR`, `[storage] directory` and `~/.claude-memory`; an organisation pins it in its managed file. `bettermemory security audit` and `bettermemory doctor` warn when the store was chosen this way, and the audit grades a store or keys directory inside a git working tree or a synced folder. Such a store can also carry the id of a store on this host, and the key ring names its key, head checkpoint and origin anchor after the id alone. The id is in every `log export` line, every `log anchor` and every bundle manifest, and a committed store's is public. The first writing open of the repository's store then retires the other store's current key for a new one, and a high seq in its log pushes the shared head past the other store's log, which afterwards opens without its key and reads `tampered` (head `tail_deleted`). `cwd_store = false` closes that route; binding the key ring to more than the id is not done in this release.

**An organisation's managed config** (9.0.0rc12). A managed file, `/Library/Application Support/bettermemory/managed.toml` on macOS and `/etc/bettermemory/managed.toml` on Linux and every other POSIX system, takes config.toml's sections and keys, and every key it sets is pinned: the user's config.toml cannot loosen it, so an agent that edits that file cannot change a pinned telemetry switch, give itself back the escape hatches `[policy]` took away, re-enable `cwd_store` or clear `strict_provenance`. No environment variable moves the file, bettermemory never writes it, and it fails closed: a file that exists but cannot be read, is not TOML or holds an invalid value stops the config from loading, and the daemon does not start. What it is not: a boundary against the account. A process running as the user can export `BETTERMEMORY_DIR`, which decides the store ahead of a pinned `[storage] directory`, build a configuration in code, or open the store file directly. A daemon reads the file at its start, so a change takes effect at the next daemon start. No managed file is read on Windows in this release: a standard account can create folders under ProgramData, so a file there could be one user's, binding every other account, and it waits for a check of its owner and ACL.

**A malicious memory body crafted to exploit a parser bug.** The 8.x migration and the mirror parse and render YAML frontmatter; the server itself does not. The vendored parser (`src/bettermemory/_frontmatter.py`) uses `yaml.SafeLoader` exclusively, caps the YAML region at 64 KB and the file at 1 MiB before parsing, and refuses alias expansion on dump, so a hostile file exhausts a bounded budget and fails cleanly.

**Instructions inside a memory.** A memory body is data the model reads, and a body can contain text shaped like instructions. bettermemory delivers bodies through tool calls the model makes (`memory_show`, `memory_search`, and the episode handoff with `include_bodies=True`); the session brief and the prompt recall inject pointers (an id, the body's first 80 characters as a summary and, for the recall, a matched snippet of at most 100), never a whole body, under a header that says they are pointers, not instructions, and the handoff never delivers the body of an episode whose pointer does not verify. Every delivery carries the verification block and the provenance label beside the text so the model has the signals to weigh it. What no label can see is an injection-driven legitimate write: a memory the model was talked into writing through the gates reads `local`, truthfully. Cause provenance, what was in context when the model wrote, is the open question behind the label and is not solved today.

**An agent that changes the user's rules.** A standing memory, a ruling or rule the user gave (`ambient`, or a standing answer at or above 0.30; see `docs/api.md`), is replaced, edited, removed, demoted or taken out of force through the tools only with `said`, the user's words for the change, in any project. The daemon checks the words as it checks a join's: the quote is in a prompt the prompt hook saw in the caller's checkout; where no hook saw the checkout the words are taken as given and the reply and the log row say so. Nothing about the words' meaning is read. Every such change is one signed `standing_guard` row with the door, the memories and the quote, so a wrong one is found and reverted; since 9.0.0rc12 the row is written even with `[telemetry] enabled = false`. The write gates' own escape hatches are parameters the agent sets (`force`, the `acknowledge_*` flags), and `[policy] forbid_force` and `forbid_acknowledge` take them away: a call that passes a forbidden one is refused whole and writes nothing. What the guard holds out is an agent that forgets or overreaches through the tools, including one talked into it by text it read. An agent that runs as the user with a shell holds the store's key and is the user as far as the store can tell: it can reach the store through the `bettermemory` CLI or the file itself, and it holds the daemon's token, so it can post a prompt of its own to the hook endpoint and the daemon keeps that as the user's words. No tool check holds it out, and a daemon under a separate OS account would not either: that account would keep the file, the key and the log out of the agent's reach, but the agent's account would still hold the token the hook and the shim need, and with it the words channel. The line is the harness's to draw, between the hooks and MCP servers it runs with the user's access and the shell it gives the agent. Claude Code's sandbox draws it when it is on and locked: inside it the agent's shell reaches neither the daemon's port, the store, the key nor the token, the hooks and the shim run outside it, and the only words the daemon holds are the ones the prompt hook posted. `docs/installation.md` names the settings, `bettermemory security sandbox` prints them for this host's own paths, and `bettermemory security audit` compares what Claude Code's settings files hold against them.

**Session capture.** With `[capture] stop_checkpoint = true` (off by default, Claude Code only), the Stop hook periodically hands the chat model an instruction to save what the conversation established, and the model writes memories from its own context. That is a write path a conversation's content can steer, so it is bounded on every side: only a session a person is attending is asked, at most `daily_cap` times per store per day; the writes pass every gate above with no `force` and no acknowledge flag honoured, plus the enforced capture rules (no to-dos, no drifting counts, absolute dates, a plain subject); each write carries the review's `unsafe` and `secret` scores and the unanswered relations are settled in the batch's closing call; and every capture is a batch on the signed log that `bettermemory capture review` lists and `capture undo` takes back, after which the same body is not captured again. A captured memory reads `local`, like any write the model made.

### Out of scope

These would not be treated as security issues:

- "I edited the store file and lost data." The file is SQLite; edit it with the tool, or with `sqlite3` knowing the audit will report the edit.
- "Anyone with read access to my home directory can read my memories." Yes, by design. Memories are plaintext on disk. Use OS-level disk encryption (FileVault, LUKS, BitLocker).
- "The daemon serves any local process that presents its token." Yes, by design; see the daemon and the client that lies about who it is, above.
- "A process running as me signed a row." Yes, by design; see the process that holds the key, above. Deciding what is true is the model's and the user's job, with the signals the read surfaces carry.
- "A process running as me moved or deleted the origin anchor or the head checkpoint." Yes, by design; they sit in the keys directory beside the key, and a process that can write there holds the key. External anchors (`log anchor`) are the evidence that survives it.
- "A process running as me set `BETTERMEMORY_DIR` past the managed file." Yes, by design; see the organisation's managed config, above.
- "A process running as me posted a prompt to the daemon's hook endpoint, and the guard took it as my words." Yes, by design; see the agent that changes the user's rules, above. The hook channel is the account's, and the harness's sandbox is what keeps the agent's shell off it.

## Hardening notes

- **One writer at a time.** The store opens in WAL mode with a 5-second busy timeout. The daemon holds one connection on its event loop and one per worker thread, every mutation is one transaction, and a second writer waits rather than interleaving. The store itself takes no lock file; the daemon holds `daemon-<hash>.lock` in the state directory for its life, which is what keeps one daemon per store, and the key ring writes the head checkpoint and the origin anchor under sidecar locks.
- **Git shelling.** `origin.py` calls `subprocess.run` without `shell=True` and with an explicit argv list; output is parsed defensively (the git remote URL is run through `urlparse`) and decoded as UTF-8 explicitly.
- **Credential refusal at write.** `memory_write` and `memory_update` refuse a body carrying a secret-shaped token (API keys, PEM blocks, JWTs, `password=` assignments) unless the caller acknowledges it as a documented example; `[policy] forbid_acknowledge = ["credential"]` takes that acknowledgement away. Since 9.0.0rc12 `episode(action="write")` runs the same detectors over the body and the takeaway and refuses a hit outright, with no acknowledge flag. The event records only the detector kinds, never the value.
- **Finding a secret that got in** (9.0.0rc12). `bettermemory security scan` runs the write gate's detectors over every text field of the memories, tombstones, episodes and conflicts tables, and with `--log` over every log payload, and reports where each hit is, the record's state and whether the write was acknowledged, never the value. It does not read freed pages or earlier page images in the store file and its WAL, the full-text index's pages, saved orphans, backups or exports, so a clean scan is not a clean file. The signed log keeps every version of every record, and no command erases a log row: a secret that reached the log stays in the store file and in every backup of it, and the remedy is to rotate the credential.
- **Query redaction in the log** (`events.py`). Every `query` / `probe_query` field is stored as `{"hash", "preview", "len"}` rather than verbatim text, and `redact_query` replaces secret token shapes with opaque markers before the 32-char preview is taken: the five legacy shapes (Anthropic `sk-ant-…`, OpenAI `sk-…`, GitHub `ghp_…` and `github_pat_…`, AWS `AKIA…`), and since 9.0.0rc12 every shape the write gate detects, as `[REDACTED:<detector kind>]`. Previews written by an earlier release are not rewritten. There is no verbatim mode. The migration redacts every 8.x event the same way on import.
- **Audit rows with telemetry off** (9.0.0rc12). `[telemetry] enabled = false` keeps telemetry out of the log, but not the audit rows: a `standing_guard` row, and a `write` or `update` row that used `force` or an acknowledge flag, is recorded either way.
- **The key file.** Created `0o600` under a `0o700` directory, read once at open, never logged. A store whose key is lost is readable and unverifiable; there is no recovery path that re-signs history, by design. The head checkpoint (`<store_id>.head`) and the origin anchor (`<store_id>.origin`) sit beside it at the same modes.
- **Backups** (9.0.0rc12). `bettermemory backup create` writes a bundle directory `0o700` with files `0o600`, and signs its manifest with the store's key, which stops someone without the key from editing a bundle (truncating its log and rewriting the hashes to match); it does not stop the substitution of an older genuine bundle, and it does not help against a key holder, which is what external anchors are for. The signature counts only under a key the keys directory holds. A bundle can carry a key, and anyone who can write a bundle can remake it under a key of their own and sign it with that: `backup verify` reads such a bundle `unverifiable` (signature `self_signed`), and `backup restore` refuses it, since restoring it would make the bundle's key the store's current key and retire the one held, unless `--trust-bundle-key` is passed. Without `--include-key` a bundle verifies and restores only where the key is held, so keep the keys directory backed up apart from the bundles; with it, anyone holding the bundle can sign rows as the store, and on a machine that does not hold the key it restores only with `--trust-bundle-key`, which is worth what the place the bundle was kept is worth. The default bundle directory sits inside the store directory, on the same disk, where anything that can write the store can write the bundles: keep bundles you will restore from somewhere only you can write.
- **Posture checks** (9.0.0rc12). `bettermemory security audit` reports, read-only, the modes and owners of the store, its WAL files, the keys, the head and origin files and the daemon's state and log; the key against the store; the store and the keys outside git working trees and synced folders; and Claude Code's sandbox settings against what `security sandbox` would print. It reads only file-based Claude Code settings (the managed-settings files and the user's), not server-managed settings or MDM sources, which Claude Code ranks above them. File modes are not checked on Windows.
- **Supply chain** (9.0.0rc12). Every workflow action is pinned by commit with its version in a comment; top-level workflow permissions are read-only and write scopes are granted per job, only to the jobs `tests/test_workflow_policy.py` lists; no checkout keeps its token, and no untrusted expression is expanded inside a `run:` script. The build backend is pinned (`hatchling==1.32.4`), and the release build runs without the uv cache. A release carries `SHA256SUMS`, a GitHub build-provenance attestation and a CycloneDX SBOM of the lock, besides PyPI's own attestations (`docs/release.md`, "Verifying a release"). `mcp-publisher` is pinned and checked against its release's checksums before it runs. CodeQL, OpenSSF Scorecard, an OSV audit of `uv.lock` and a license check run in CI; none gates a release.

### Controls that no longer apply at HEAD

Recorded because a reader scoping the attack surface should know these are gone rather than unguarded.

- **Sync admission and quarantine** (6.6.0 through 8.x). `bettermemory sync` replicated the store over a git remote, and every pull was judged by a size cap, the parser, an id-alias check and the credential gate, with refusals quarantined. 9.0 removed the sync lane whole, with the admission chain; the `quarantine` table stays in the schema for the lane's return.
- **Content evidence over files** (7.3.0 through 8.x). Every store write recorded the SHA-256 of the file it wrote beside the index row, and the 8.x `bettermemory doctor` named files whose bytes changed with no store write behind the change (the `doctor` 9.0.0rc12 adds is a different, read-only self-check). The signed log and the per-row pointer replace it: the evidence is now on every row and checked on every read, not on a rebuild.
- **Web UI CSRF gate** (2.0 through 4.x, `bettermemory ui`). 5.0.0 removed the web module. The 9.0 daemon's HTTP surface is covered in the threat model above.
- **`np.load(allow_pickle=False)` on the semantic-dedup cache** (through 3.x). 4.0.0 removed the module and numpy itself.
