# bettermemory v1.6 plan (historical)

_Date drafted: 2026-05-16._

> **Status: shipped as v2.0.0 on 2026-05-16.** Nine of the ten tiered features below (T1.1, T1.2, T1.3, T2.1, T2.2, T2.3, T3.1, T4.1, T4.3) landed in one major release rather than the planned 1.6 → 1.7 → 1.8 sequence. T3.2 (embedding cache pruning) and T4.2 (team scopes with ACLs) remain unshipped. See the [2.0.0 entry in `CHANGELOG.md`](../CHANGELOG.md) for the as-shipped detail. This document is preserved as the planning record for the design rationale behind each feature.

The goal for the 1.6 → 1.8 sequence was to close the recall, write-safety, and scale gaps in the v1.5 surface so bettermemory was usable on larger corpora and harder workloads.

---

## Where v1.5 stood

17 MCP tools, fsync-hardened, ~790 tests, MIT, plain-markdown storage. Three properties carried over into 2.x as load-bearing design choices:

1. **First-class verification with structured attestation** — `memory_verify(verified_paths=[...], verified_commits=..., verified_versions=...)`. Persistently records *what* was spot-checked, not just *that* something was.
2. **Opt-in retrieval as a contract** — the model searches when context is needed, the default per turn is not to search. The structural answer to auto-injection failure modes.
3. **Pending-confirm tier for `category="user-inference"`** — claims about the user always require user veto before commit.

Plus a `staleness_verdict` rollup on every retrieval (calendar + filesystem + commit drift folded into one field), tombstone-aware dedup, scope_mismatch gating, auto-`record_use` lifecycle, and worktree-aware auto-scoping.

## Landscape snapshot (May 2026)

A reference list of related projects at the time of the plan. Each occupies a different point in the storage / retrieval / interface design space:

- **Anthropic Memory Tool** — files (host-implemented), list+read only, no search. Claude self-organizes via filenames.
- **mem0** — vector DB with optional Neo4j graph backend, explicit `search()` API plus add-on patterns for context injection. Temporal reasoning over time-tagged memories.
- **Letta (MemGPT)** — core / recall / archival tiers with tool-routed access; sleep-time consolidation via a dual-agent pattern.
- **Zep / Graphiti** — temporal knowledge graph with BM25 + vector + graph search, bi-temporal (`t_valid` + `t_created`). Graphiti is the open-source backbone.
- **Cognee** — graph + vector + SQL, multiple retrieval modes via explicit search. OWL-class entity validation.
- **Memori** — SQL-backed (BYO Postgres / MySQL / SQLite), structured queries; small but explicit pipeline.
- **mcp-memory-service** — sqlite-vec / Milvus / hybrid backends, BM25 + vector RRF, typed edges.
- **Engram** — Go + SQLite FTS5, full-text + semantic; What/Why/Where/Learned schema.

Academic systems consulted in the same pass: **MemoryOS** ([arxiv 2506.06326](https://arxiv.org/abs/2506.06326), three-tier OS-style heat eviction), **A-MEM** ([arxiv 2502.12110](https://arxiv.org/abs/2502.12110), Zettelkasten with memory evolution), **HaluMem** ([repo](https://github.com/MemTensor/HaluMem), first operation-level write-time hallucination benchmark).

---

## The thesis

The field is splitting three ways:

- **Graph-heavy** (Zep, Cognee, mcp-memory-service) — rich joins at the cost of infra weight
- **Vector-heavy** (mem0) — paraphrase recall at the cost of write-time hallucination risk
- **File-heavy** (Anthropic) — grepability at the cost of curation surface

bettermemory occupies a fourth path: **a small, file-backed system with strong write-time gates, structured verification, and an explicit retrieval contract.** The 1.6 → 1.8 plan triples down on the verification surface and closes two gaps users hit at scale: keyword-only recall and a `load_all` ceiling around 5–10K memories.

## Feature plan, ranked

### Tier 1 — Recall accuracy and write safety

#### T1.1 — Provenance / citation on retrieval

When a retrieved memory shapes a response, emit a structured citation: `{memory_id, claim_excerpt, last_verified_at, verified_paths}`.

Surface via either:
- a new `memory_cite(memory_id, claim)` tool, or
- a field on `memory_record_use(outcome="applied", claim_excerpt=...)`.

Closes the audit-trail gap that turns hallucinated stored facts into hard-to-trace bad responses.

#### T1.2 — Hybrid retrieval: BM25 + Jaccard + optional vector via RRF

Jaccard is fine for keyword-heavy queries but loses on paraphrase. Add BM25 on the same tokenizer (zero new deps), reciprocal-rank-fusion with semantic when extras are installed. Files remain canonical.

Closes the recall gap on paraphrased queries without changing the storage model.

#### T1.3 — Write-time hallucination gate (`groundedness_check`)

`memory_write(groundedness_check=True, source_transcript=...)`: compare the proposed body's claims against the recent turns. Claims without grounding return `status: "ungrounded"` with the unsupported phrases listed — same family as `transient_warning` / `scope_mismatch` / `duplicate`.

HaluMem made operational at the write site.

### Tier 2 — Curation and link graph

#### T2.1 — `bettermemory consolidate` CLI

Offline curation pass. One command that:

- semantic-similarity dedups near-duplicates (extras already in place)
- demotes never-applied memories to `category=ambient`
- ages out cold scopes (suggest, don't auto-delete)
- resolves scope-typo pairs from the Levenshtein detector
- dry-runs by default, `--apply` to commit

Covers the sleep-time-compute idea without needing a second agent or a background loop.

#### T2.2 — Typed inter-memory links

Add `links: [{type: "supersedes"|"contradicts"|"extends"|"depends_on", target_id, note}]` to the memory record. In `memory_search`, optionally suppress `supersedes`d results; flag mutual contradictions.

Adopted from mcp-memory-service's typed-edges idea, but plumbed into retrieval, not just storage.

#### T2.3 — Negative-results memory

When `memory_record_use(outcome="ignored"|"contradicted")` fires, subsequent searches for similar tokens annotate matching results with "this was rejected on $date" so the model doesn't keep re-suggesting the same junk.

### Tier 3 — Scale (remove the 5–10K linear-scan ceiling)

#### T3.1 — SQLite FTS5 inverted index, files canonical

Index is a derived cache; markdown remains source of truth. Rebuilt by `bettermemory reindex`. Removes the `load_all` bottleneck without losing grep / git-trackability.

#### T3.2 — Embedding cache pruning

Auto-prune entries whose memory was removed or whose body changed.

### Tier 4 — Sync, sharing, UI

#### T4.1 — `bettermemory sync push/pull` between hosts

Git-style replication of the memory store. Per-host origin tracking already exists. Brings memory along when the user moves between machines.

#### T4.2 — Team scopes with simple ACLs

`team:<name>` namespace where multiple agents read but one writes (or RBAC via `.acl`). Cross-agent shared memory without a managed service.

#### T4.3 — Local web UI: `bettermemory ui`

Local-only FastAPI + tiny SPA. Browse, verify, view audit timelines. Optional; CLI remains primary. Killer use-case is the curation surfaces (`dead_weight`, `contradictions`, `never_verified`) where a UI beats a tool call.

---

## What to cut

- **No graph DB.** Other projects carry that weight well; bettermemory's design is deliberately not-that. T2.2 (typed links) is graph-lite without the infra.
- **No auto-extraction from conversation.** The opt-in retrieval contract loses its meaning if writes happen behind the user's back.
- **No managed cloud.** Plain-text on disk + git-based sync is the alternative.

---

## Suggested release sequencing (as planned)

- **1.6.0** — T1.1 (provenance) + T1.2 (BM25/RRF) + T2.1 (consolidate). _"Recall becomes more accurate and more accountable."_
- **1.7.0** — T1.3 (write-time gate) + T2.2 (typed links) + T2.3 (negative results). _"Writes get safer, retrieval gets smarter."_
- **1.8.0** — T3.1 (FTS5 index) + T4.1 (sync) + T4.3 (web UI). _"Scales out — bigger corpora, across machines."_

In practice, the three releases collapsed into 2.0.0.
